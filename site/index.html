UmbrellaAAR

A Gradle plugin that merges the local modules of your Android or Kotlin Multiplatform project into one AAR.

Only local modules are merged. External dependencies stay external and land in the POM.

  • Gradle Plugin Portal

Current version 3.0.0

Declare the Kotlin and Android plugins in your root build with apply false, or replace these lines with your version catalog aliases.

How it works

You apply the plugin to one Android library module, the umbrella module, and name other modules with export. From there the plugin follows api, implementation and runtimeOnly project dependencies through the source sets that reach the Android main compilation, so you only name the entry points.

It takes each module's archive, rewrites references to merged R classes so they point at your umbrella namespace, and merges everything into the umbrella module's own AAR.

External libraries are never unpacked. Add the companion POM plugin and they are listed in the published POM, so your consumers resolve them as usual.

Quick start

Pick the Android library module you want to ship. This is your umbrella module. The other modules need no source changes. For their sources to ship as well, see Merged sources.

  1. Apply the plugin

    Add the umbrella plugin next to the Kotlin and Android plugins, in any order.

    AGP requires namespace and compileSdk here and stops with an error without them. androidLibrary is the older, deprecated name for the android block. The repository's samples still use it, and both work.

    The plugin resolves from the Gradle Plugin Portal and Maven Central, so it needs no extra repository if your pluginManagement block already has gradlePluginPortal() or mavenCentral(). The Kotlin and Android ids above carry no version. Declare the Kotlin and Android plugins in your root build with apply false, or replace these lines with your version catalog aliases.

    Tasks are registered only when com.android.library or com.android.kotlin.multiplatform.library is applied to the module. On com.android.application you get the export configuration and no tasks.

  2. Declare what goes in

    This goes at the top level of the build file. export takes local projects and platforms. An external coordinate on export fails the build, because it would not be merged. So do files(...) and a project asked for a capability, a configuration or attributes, or with isTransitive = false.

  3. Run the task

    bundleDebugUmbrellaAar is the debug task. On a Kotlin Multiplatform umbrella, both come from the same androidMain output. The same export block and task names work on a com.android.library umbrella.

  4. Find the output

    The file name is the project name plus the lowercase variant. For sources, run androidReleaseUmbrellaAarSourcesJar, which writes your-library-release-sources.jar next to the AAR. The bundle task does not build it for you.

Check what went in

The task that unpacks your modules also writes a report. It is the quickest way to check which modules went in.

Each line is a merged project and the first edge that reached it, tab separated. On a com.android.library umbrella the folder is the build type, such as release, instead of androidMain. Read it after you change dependencies, and diff it between builds to catch a module you did not mean to ship.

What goes into the AAR

The merge starts from your umbrella module's own AAR, unpacked in full and kept as it is. Each dependency module is then applied on top, in the order a consumer of those modules would rank them, and in relative-path order within a module. That puts a module ahead of what it depends on, then follows the order modules are reached from export(...). Folder names play no part. classes.jar and the final AAR are written with sorted entries and timestamp 0.

One rule covers everything that is not merged, renamed, overridden or dropped. If two modules ship the same path, identical bytes keep one copy. Different bytes fail merge<Pipeline>UmbrellaAarDependencies with an error naming both contributors. <Pipeline> is AndroidMain on a Kotlin Multiplatform umbrella and the build type on com.android.library.

R references

In dependency modules, references to any merged module's R class are rewritten with ASM. com/dep/R and com/dep/R$string become <umbrella namespace>/R and <umbrella namespace>/R$string. Only namespaces read from merged AARs are rewritten, so android.R, AndroidX, Material and other third-party R classes stay intact. No class is renamed or moved.

Publishing

The companion plugin, io.github.tiper.umbrellaaar.pom, writes the POM that the AAR alone cannot carry. It does nothing unless the main plugin is applied, and it can go before or after maven-publish.

Set group and version in the module. The publications inherit them, and without them your version is unspecified.

With maven-publish applied, the plugin registers one publication per variant: androidReleaseUmbrellaAar and androidDebugUmbrellaAar. Each carries the merged AAR and the merged sources jar under classifier sources. Publish one with its own task:

Before you publish

Publish the umbrella with its own task, or give it its own coordinates

Umbrella publications set no coordinates of their own, so they default to project.group:project.name:project.version. In a Kotlin Multiplatform project the kotlinMultiplatform publication already has those coordinates, and the release and debug umbrella publications share them with each other.

Two of them going to one repository land in the same location, and the last one wins. The umbrella .aar survives, but another publication's .pom and .module replace the flattened dependency list. Your consumers then fail on internal coordinates such as Could not find <RootProject>.<path>:<module>:unspecified.

So a run that would do that fails before anything is published, naming the module, the publications and the repository. By default publish, publishToMavenLocal and a plugin's publishToMavenCentral all would. Use one of these two fixes. If one publication is meant to replace the other, set umbrellaaar.allowCoordinateClash=true in the root gradle.properties, or pass it with -P. A module's own gradle.properties is not read.

Publish only the umbrella

Run the targeted task, and leave out the lifecycle tasks while coordinates collide.

Give the publications distinct coordinates

The failure spells this out for your module. In a Kotlin Multiplatform project rename both variants: if you rename only release, debug stays on the project coordinates and still collides. On com.android.library, moving debug is enough, and so is disabling that variant.

A debug build has no use on Maven Central. To leave one out of a run that publishes everything, disable its tasks. onlyIf does not count here, as it only decides once the run is under way.

A variant disabled through androidComponents has no umbrella. publish, publishToMavenLocal and publishAllPublicationsTo<Repository>Repository leave it out, and a task of that variant fails if you name it. If a merged module disabled a variant the umbrella still needs, that umbrella fails naming the module. Enable the variant, disable it on the umbrella as well, or give the umbrella's build type matchingFallbacks. A com.android.kotlin.multiplatform.library umbrella has neither, so it also fails on a merged module left with a build type it did not ask for. Enable the variant, or add that build type to selectBuildTypeFrom in localDependencySelection.

What the POM lists

  • External dependencies declared in the api, implementation and runtimeOnly scopes of the umbrella module and every merged module.
  • Direct dependencies, resolved with Android attributes, each with scope compile. A transitive module that a platform, constraint or resolution rule moved is written too, because consumers would otherwise get the version the library asked for.
  • Local project dependencies are never written. compileOnly dependencies are left out.
  • org.jetbrains.compose.* and org.jetbrains.androidx.* coordinates become their androidx equivalent when one is resolved, and stay unchanged when none exists.
  • Each library reaches the POM once per artifact, at the version Gradle resolved for the umbrella.
  • What a module declares about a dependency ships with it, in the POM and the .module, as a stock publication writes it: exclude(...) on the dependency or on a configuration behind the selected variant, isTransitive = false, classifiers and artifact types, and requested capabilities, which only the .module can express. strictly and reject go out as a constraint on the module. A plain exclude on a dependency on a local module carries over to the external dependencies below it.
  • One entry speaks for every module declaring that dependency, and Gradle leaves a module out only if every path to it does. So an exclusion is published if all declarations carry it, and a plain declaration next to isTransitive = false stays transitive.
  • Constraints, platforms and resolution rules apply as they do when the modules are built. A platform itself is neither merged nor written. A module's own constraints on external modules are published as dependencyConstraints in the .module and dependencyManagement in the POM. Gradle consumers still pick the highest version they see, so a pin below what a library asks for does not carry over. What a platform says about a module the umbrella does not reach is lost, so a consumer that gets that module some other way gets the version it asked for. Declare a constraint on a module where that has to carry over.
  • A dependency an included build provides is published with the version that was asked for. One that nothing gives a version fails the build, bundling as well as publishing, and so does a file in a flatDir, which has no coordinates a consumer could find.
  • A dependency Gradle cannot resolve fails the build. With umbrellaaar.legacyGraph=true it is left out of the POM, with no warning, so read external-dependencies.txt before you publish. That graph publishes coordinates alone, with nothing else a module declared.

To see the list before you publish, run collectReleaseExternalDependencies. It writes build/reports/umbrellaaar/release/external-dependencies.txt, sorted, one group:name:version:scope per line. Whatever else was declared follows, as in com.squareup.okhttp3:okhttp:4.12.0:compile excludes=com.squareup.okio:*, with artifact=name:type:extension:classifier, which keeps all four fields, and capabilities=group:name alike, and a constraint has constraint for a scope, then strictly=, prefer= and reject= where it sets them. generatePomFileForAndroidReleaseUmbrellaAarPublication writes the POM itself to build/publications/androidReleaseUmbrellaAar/pom-default.xml. The Kotlin plugin adds kotlin-stdlib late, so a full publish can list it when these tasks run on their own do not.

Merged sources

The merged sources jar holds only .java and .kt entries. A file with the same path and the same bytes in two modules ships once. If the bytes differ both ship, and the one that comes later goes in a folder named after its module's sources jar. The umbrella's own files keep their paths.

The jar is built from a sources jar in each module, produced by a task such as sourceReleaseJar, androidSourcesJar or sourcesJar. A plain com.android.library module has one only with android { publishing { singleVariant("release") { withSourcesJar() } } }, so add that to each one. A plain JVM module needs java { withSourcesJar() }. On a com.android.library umbrella, add singleVariant("debug") { withSourcesJar() } as well if you publish debug, which publish does. A module without a sources jar is left out of the merged one, with a build warning naming it and the line to add. Its classes still ship and the publication goes on.

Compatibility

If you are on AGP 8, stay on the 2.x line. The 3.x line needs AGP 9. Which line you need depends on your AGP version, not on which Android plugin you apply.

Moving from 2.x

3.x no longer merges modules reachable only through compileOnly. 2.x did. 3.x lists them in a build warning, so the change is visible. Internal task names under the Kotlin Multiplatform plugin also changed. Public task and publication names did not.

Moving from 3.0

A run that would publish two publications at one set of coordinates now fails, and by default a plain publish or publishToMavenLocal does. Before you publish has the ways out.

A build script that did not change can get a different POM. A module with androidTarget() now publishes each dependency with exclusions for kotlin-stdlib-common, kotlin-test-common and kotlin-test-annotations-common, which KGP puts on its configurations, as a stock .module does. A dependency declared as @aar, or any other @ext, now publishes as not transitive, so consumers no longer get what it depends on from the umbrella. Set isTransitive = true on it to keep that. To check your own build, compare external-dependencies.txt with and without umbrellaaar.legacyGraph=true, and ignore excludes= and a kotlin-stdlib line.

android<Variant>UmbrellaAarSourcesJar still builds the merged sources jar, but it no longer has the jar as an output. To wire the jar into another task, take it from merge<Variant>UmbrellaAarSources.

A Kotlin Multiplatform umbrella now fails on a merged module left with a build type it did not ask for, where it used to ship that build.

Before you adopt it

Merging modules adds risk to your release. These are the limits to weigh first.

  • Project isolation is not supported. The plugin reads sibling projects' configurations and forces their evaluation, which project isolation does not allow.
  • Prefix your resource names per module. If two merged modules declare the same res/values resource for the same qualifier, the first stays, as in a consumer of those modules, and the merge logs a warning naming both. Attr definitions a consumer rejects with Duplicate value for resource fail the bundle, naming both modules. The plugin never compiles or links the merged resources, so anything else wrong with them only surfaces in a consumer build.
  • Test the merged AAR, especially with reflection or R8. R rewriting covers class references in the merged modules and in the umbrella module's own classes. It does not touch classes inside libs/*.jar, or string lookups such as Class.forName. Build a consumer against the merged AAR before you ship it.
  • Only local Android library and JVM modules can be merged. A module with no archive task fails the build, and the error names the project and the tasks it tried.
  • A declared export ships, or the build fails. A module in export(...) that Gradle cannot resolve fails the build before any task runs, naming the module and Gradle's reason. So does anything below it that does not resolve, two local modules sharing a group:name, a module reached through two variants, as any testFixtures(project(...)) is, and an umbrella merging another umbrella without what that one exports, which the outer umbrella has to export too. Use exclude(...) to leave one out on purpose. An Apple framework export with no Android side only gets a build warning.
  • Flavors must be selected, and no build types declared late. A merged module with product flavors needs one selected, with missingDimensionStrategy or localDependencySelection, and the umbrella module itself cannot have flavors. On com.android.library, a build type declared in your android block gets no umbrella tasks or publication, because the plugin reads build types before that block runs.
  • Debug on a Kotlin Multiplatform umbrella is not a separate build. Release and debug share one androidMain pipeline, and exported com.android.library modules contribute one AAR to both, release unless localDependencySelection selects another build type.
  • exclude on export is global. exclude(group = ..., module = ...) on any export line applies to the whole umbrella. It removes matching local modules from the merge and matching external dependencies from the POM. A module reached only through an excluded module is still merged. A rule that leaves nothing out gets a build warning, showing the real group of a local module with that name.
